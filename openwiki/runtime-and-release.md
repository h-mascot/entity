# Runtime and release

Entity keeps a set of lightweight public probes and release helpers so operators can verify the live runtime without opening a privileged session. The same page also owns the hardened OpenWiki integration, because the docs pipeline now behaves like release tooling rather than a loose side script.

The main source seams are:

- `packages/server/src/routes/core.ts` for health, version, and phase-2 diagnostic probes.
- `packages/server/src/config/runtime.ts`, `packages/server/src/config/schema.ts`, and `packages/server/src/config/runtime.test.ts` for bootstrap config, local-source allowlisting, and config-derived runtime env.
- `scripts/entity-release-info.mjs` and `scripts/entity-release-info-stdin.mjs` for release metadata. `scripts/entity-release-info-stdin.mjs` validates JSON stdin payloads before delegating to `scripts/entity-release-info.mjs`, which keeps remote metadata writes shell-safe.
- `scripts/entity-verify-sandbox.sh`, `scripts/entity-deploy-sandbox.sh`, and `scripts/entity-promote-prod.sh` for deployment checks and promotion flow. The sandbox and deployment scripts now enforce exact release identity through the checked-out branch and SHA, and the GitHub workflow verifies generated docs against the pull-request head rather than the merge commit.
- `scripts/entity-openwiki.mjs`, `scripts/entity-openwiki-lib.mjs`, `scripts/entity-openwiki-html.mjs`, and `packages/app/scripts/entity-openwiki-html-lib.mjs` for local OpenWiki generation, HTML presentation rendering, isolated credential handling, fingerprinting, and verification. `scripts/entity-wiki-config-migrate.mjs` updates older configs so the `entity-wiki` source points at `./openwiki-html` instead of the generated wiki input tree, and `packages/server/src/fs/classify.ts` plus `packages/server/src/fs/index-runner.ts` strip HTML tags and entities before indexing the generated presentation pages. `scripts/entity-release-info-stdin.mjs` is the JSON-over-stdin wrapper that validates release identity payloads before delegating to `scripts/entity-release-info.mjs`, which keeps remote metadata writes shell-safe. `scripts/entity-runtime-env.mjs` serializes the runtime environment allowlist that deployment scripts write to disk, with `RUNTIME_ENV_KEYS` defining the exact set of runtime variables that are preserved when `ENTITY_BASE_URL` is canonicalized and `serializeRuntimeEnv` rejecting non-canonical origins instead of passing them through. The same file-source work now shares the 16 MiB bounded-read ceiling used by the local and HTTP markdown adapters, so release/runtime guidance and the Files page describe one consistent source-read boundary. The release-manifest tests now lock in the identity contract: `package-lock.json` is hashed by link text instead of resolved bytes, `artifactHash` ignores mutable runtime files such as `.env`, SQLite WAL/DB state, and log files, `distHashes` are computed per shipped dist root, and retargeting a symlink changes the relevant hash while mutating bytes behind the same link does not. `packages/app/src/lib/htmlPreviewPolicy.ts` now keeps the `entity-wiki` preview scriptless while other HTML sources retain the richer sandbox, and `packages/app/src/components/CodeMirrorFileViewer.tsx` reloads the same iframe node once after a deep-linked load so fragment navigation remains stable inside that static preview. The same OpenWiki path now includes `docs:wiki:render` output under `openwiki-html/`, and `scripts/entity-openwiki.mjs` treats that rendered tree as part of `prepare` so freshness checks cover both the Markdown source wiki and the published presentation tree.
- `packages/app/src/lib/htmlPreviewPolicy.ts` now makes the `entity-wiki` HTML preview use a static sandbox with no script execution, while interactive HTML sources keep the richer preview sandbox; `packages/app/src/components/CodeMirrorFileViewer.tsx`, `packages/app/src/views/DocumentEditorView.tsx`, and `packages/app/src/views/MobileView.tsx` consume that policy so the viewer and mobile shell preserve safe fragment navigation for generated wiki pages without widening the preview surface. `CodeMirrorFileViewer` now rebuilds the static preview object URL when the route hash changes and reloads that same iframe node once after a deep-linked page loads, so browser scroll restoration cannot override the requested fragment while the preview stays scriptless and React retains ownership of the DOM node. The release-side file-reading work also tightened the shared bounded-read helper used by local, HTTP markdown, and docsify adapters, which keeps the 16 MiB source-read ceiling aligned with the Files page and ensures oversized source reads fail consistently at the server boundary. This page is also the canonical home for the OpenWiki render and release flow, including `scripts/entity-openwiki-html.mjs`, `packages/app/scripts/entity-openwiki-html-lib.mjs`, `scripts/entity-wiki-config-migrate.mjs`, `scripts/entity-release-info-stdin.mjs`, and the release-manifest identity contract that records branch, git SHA, artifact hashes, and dist hashes for shipped build outputs. `package.json` wires the commands that tie those checks together.

## What operators can verify

- Whether the server is alive at `/api/health`.
- Which release identity is currently running at `/api/version`.
- Phase-2 diagnostic state when that feature set is enabled.
- Whether a sandbox deployment matches expected release information before promotion.
- Whether a production promotion step should proceed.
- Whether committed OpenWiki content matches the current source fingerprint before sandbox or production shipping continues.

## Probe flow

`packages/server/src/routes/core.ts` exposes the public probes used by the README and deployment scripts. The health route returns a simple `status: ok` payload, while the version route returns release information read from the repo’s release metadata helper.

The OpenWiki toolchain now treats docs freshness as a release boundary. `scripts/entity-openwiki-lib.mjs` computes the source fingerprint that is written to `openwiki/.entity-openwiki.json`; the fingerprint includes the repo roots that are meant to ship, ignores private env files and ignored directories, and now explicitly counts tracked source nested under `build` and `dist` path segments. That nested-source coverage was finalized in `scripts/entity-openwiki-lib.test.mjs`, which exercises `packages/server/src/build/manifest.ts` and `packages/app/src/dist/fixture.ts` so shipped source in those paths still changes the fingerprint.

  participant Operator as operator or deploy script
  participant Server as /api/health or /api/version
  participant Release as release-info helper

  Operator->>Server: GET /api/health
  Server-->>Operator: status ok + uptime + timestamp

  Operator->>Server: GET /api/version

  Server-->>Operator: version payload

## Release and deploy commands

The root package scripts expose the canonical automation entrypoints:

- `npm run verify:sandbox`
- `npm run deploy:sandbox`
- `npm run ship:sandbox`
- `npm run promote:prod`
- `npm run release:info`
- `npm run release:check`
- `npm run docs:wiki:init`
- `npm run docs:wiki:update`

The release and deploy scripts are source evidence for a real release process, but they do not by themselves prove production rollout. For rollout status, the repo treats release metadata and deployment receipts as authoritative. ### Release hash semantics

`scripts/entity-release-info.mjs` writes two files in the release tree: `RELEASE.json` (the manifest) and `VERSION` (the `gitSha` on its own line). The manifest records the identity of a built release so operators can verify that a deployed checkout matches its expected source. The hashes are computed with a symlink-aware walk so that mutable runtime state never corrupts an immutable artifact identity:

- `packageLockHash` inspects `package-lock.json` with `lstatSync`. When that path is a symlink, only the link text (the `readlinkSync` target string) is hashed, not the bytes of the resolved target. A retargeted symlink therefore changes the hash even when the resolved content is byte-identical.
- `artifactHash` is a content tree hash of the repo root with `['.git', 'node_modules', 'output']` excluded. `packages/app/dist`, `packages/server/dist`, and `packages/db/dist` are included in the root walk only as ordinary tree entries; their immutable contents contribute to `artifactHash`.
- `distHashes` is computed per `packages/{app,server,db}/dist` root via `maybeTreeHash`. Each dist root is `lstatSync`-inspected: a symlinked dist root is hashed as a single path record (its link text, not its target bytes), so retargeting a dist symlink alters the dist hash while mutating files beneath the target does not.
- Within every tree walk, `walk` sorts directory entries by name and emits each record domain-separated as `relativePath\0`, `kind\0`, then `payload\0`, where `kind` is `file` for regular files and `symlink` for links (whose payload is `readlinkSync` link text). This keeps path, entry kind, and payload as distinct hash domains. Replacing a symlink at the same path with a regular file containing the old symlink marker bytes changes artifactHash and distHash because kind is domain-separated.
- Mutable runtime exclusions are release-relative and scope-aware. The `repo` scope (used for `artifactHash`) excludes the top-level `RELEASE.json`, `VERSION`, `.env`, `packages/server/.env`, and `packages/server/dist/.env`, and skips anything under `packages/server/dist/` matching a mutable runtime name. The `server-dist` scope (used for `packages/server/dist` alone) applies the runtime-name filter directly. The runtime-name test is `name === '.env'` or `name` ending in `.db`, `.db-shm`, `.db-wal`, or `.log`.
- `maybeTreeHash` returns `null` only when the root is missing (`ENOENT`); for a regular-file or symlink root it delegates to `maybePathHash`, and it tree-hashes a directory root. `maybePathHash` returns `null` only when the path is absent, and otherwise hashes a regular file's bytes or a symlink's link text. A missing or genuinely-absent root therefore produces a stable `null` rather than throwing. Domain separation guarantees that replacing a symlink at the same path with a regular file containing the old marker bytes changes both `artifactHash` and the relevant `distHash`, because `kind` is a distinct hash domain from the payload: a symlink and a regular file at the same relative path hash to different records. Mutating bytes behind a symlink while its link text is unchanged leaves the relevant hash stable, but retargeting the symlink (or swapping it for a regular file) changes it.

Because mutable runtime state is excluded by policy rather than by accident, the hashes are designed to be stable across metadata-only writes: changing `.env`, a `.db`/`-wal`/`-shm`/`-log` file, or mutating bytes behind a symlink while its link text stays unchanged leaves hashes stable, whereas changing the link text (retargeting) changes the relevant hash, while any change to immutable shipped source (including a nested `packages/server/skills/.../VERSION` file) alters the corresponding `artifactHash` or `distHash`. `--check` compares `RELEASE.json.gitSha` against `VERSION` and the release directory basename, and `--write` persists both files in the target release tree. `npm run test:release-deploy` (`node --test scripts/entity-release-info.test.mjs`) is an explicit CI hard gate: the workflow runs it directly and a failure fails the run.

## Change notes for future agents

When changing runtime or release behavior, inspect both the server probes and the shell scripts that consume them. If you touch the release identity format, keep the API route and the verification script in sync. For OpenWiki changes, update the integration page here first; it is the canonical home for the generation, prepare, and verify flow. If the prepare path changes again, keep `scripts/entity-openwiki-lib.mjs`, `scripts/entity-openwiki.mjs`, and `scripts/entity-release-check.sh` aligned with the docs so sandbox shipping, freshness verification, and release safety stay convergent.
