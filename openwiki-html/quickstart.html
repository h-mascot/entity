Entity Quickstart

Entry point to Entity, an AI-native workspace for files, tasks, agents, collaboration, execution providers, plugins, and operational proof.

entityquickstartproductengineering

Entity is a local-first, server-backed workspace where humans can inspect, steer, and review agent work. Its implemented product surfaces bring tasks, files, documents, agent state, activity, chat, services, plugins, and operational evidence into one React application. Source presence does not prove deployment rollout: /api/version, release metadata, sandbox validation, and deployment receipts remain authoritative for any live environment. The release/runtime boundary now also owns the exact-SHA sandbox handoff and the pull-request-head docs gate, which are documented on Runtime and release.

Start locally

Prerequisites are Node.js 20+ and npm.

npm install
npm run setup
npm run build
npm run doctor
npm run dev

Open http://localhost:3000. npm run setup creates local configuration, seeds the read-only Entity Wiki local file source at ./openwiki-html, and normally prepares the optional ClickClack chat sidecar; use npm run setup -- --skip-clickclack when only the core workspace is needed. The Express server serves the built frontend, so rebuild packages/app after UI changes unless using the separate Vite development loop documented in README.md.

The default configuration is loopback-only and local-first. Do not expose it on a network without understanding the security boundary.

What users can do

Surface Implemented capability Important boundary
Files Search and filter configured sources, browse trees, open tabs, read and edit source-backed files, and enter collaboration views Multi-source home is controlled by VITE_ENTITY_FS_MULTISOURCE; cached reads can mask an unavailable source
Mission Control Create, assign, move, filter, review, gate, comment on, and inspect tasks across Kanban, Insights, and Strategic views A recorded handoff does not itself prove an agent runtime was dispatched
Agents Inspect registry identity, focus, model/runtime metadata, work, health, metrics, and activity; invoke limited runtime controls when eligible Registry failure degrades management details; safe controls require a bound Helm-managed runtime
Services View plugin-supplied service families, health, latency, links, and degraded/offline states The entity-services plugin and its compiled frontend mount must both be available
Chat Use channel/thread UI and model-routing plumbing ClickClack compatibility routing is optional and sidecar-dependent
Admin Configure workspace behavior, file sources, Task Master, document credentials, plugins, TTS, integrations, agent registry, chat-management controls, presentation, and users & roles Not every setting is hot-reloadable; bootstrap path changes require restart

The Files and documents experience connects source browsing to native document collaboration, task output links, document conversion from writable local sources, and the new provider-neutral document integration surface. That surface is implemented through /api/document-integrations, the provider repositories and adapters under packages/server/src/document-providers/, and the Admin document-provider settings, which now enforce write-policy and destination checks before create or mutation requests proceed. The page also reflects the read-only local-source bootstrap path for the Entity Wiki source plus the legacy file-route hardening that blocks oversized reads and write-through aliases. The local file-source path now reuses a pooled managed-storage broker per executable and root, preserves typed missing-root and invalid-path messages, and applies the same 16 MiB read ceiling as the other source adapters, while the latest broker lifecycle fix keeps spawn failures and exit races fail-closed instead of leaving pending requests unresolved, so local browsing and release/runtime guidance now share a single file-boundary story. Mission Control owns execution planning, accountability, comments, reviews, gates, handoff records, and the grouped workspace navigation that now sends Files and Chat to one group, Tasks and Services to another, Agents to a third, and Admin to its own tab. Mission Control also picked up the browser-navigation task route seam in packages/server/src/routes/tasks.ts, while the task-detail Run with agents action and the /swarm/* execution routes remain part of the task workflow. The task-detail Handoffs section is also part of this surface and now merges direct local handoff history with canonical history rows from the server, while cloud-mode requests still fail closed with 503 cloud_handoffs_unavailable. The Agents and activity surface joins registry data with health and activity rather than treating agents as transient chat sessions. Admin and extensions is the canonical page for principals, scoped grants, file sources, settings, plugins, services, the first-admin bootstrap binding, the document-provider controls, the chat-management controls, and the read-only local-source protections, while Configuration, Admin, Plugins, and Services remains the canonical services/configuration page and explains the entity-services refresh contract, including refresh=1 and refresh=true force refreshes, the /, /status, and /registry handlers, usable stale snapshots, and the refreshing partial state while discovery is still settling. Runtime and release is the canonical home for the hardened OpenWiki integration, release checks, and docs freshness rules, including isolated credential-file HOME handling, supported-provider validation, exact-SHA sandbox handoff, pull-request-head docs verification, complete shipped-source fingerprinting, HTML presentation rendering into openwiki-html/, scriptless static-preview fragment restoration for the Entity Wiki source, the scripts/entity-wiki-config-migrate.mjs bootstrap path update, exact clean-checkout identity checks, cross-platform remote Node discovery, truthful detached gateway branch identity checks against exact origin branch refs, credential-free proxy handling, JSON-over-stdin release metadata dispatch through scripts/entity-release-info-stdin.mjs, and guaranteed cleanup of the isolated HOME even when pnpm install or OpenWiki fails. It now also documents the release-manifest identity contract and its focused tests: symlink-aware hashing for the repo tree, package lock, and dist roots; exclusion of mutable runtime files such as .env, SQLite WAL/DB state, and log files; and proof that retargeting a symlink changes the relevant hash while mutating bytes behind the same link does not. The same page now covers the docs:wiki:render presentation tree and the scripts/entity-wiki-config-migrate.mjs bootstrap update to ./openwiki-html, so the runtime/release page is the canonical place to check OpenWiki generation and deployment behavior. It also covers the new bounded readiness poll helper and the managed-storage broker hardening that keeps deployment restarts and file writes fail-closed at the server boundary. Entity refreshes OpenWiki before sandbox shipping on the trusted Enterprise runner, and GitHub Actions now verifies that committed generated docs remain fresh against the pull request head rather than the merge commit, including fork-aware head checkouts on pull requests. The latest audit evidence for that loop is metadata-only: docs/plans/evidence/entity-document-integrations/T-001/AUDIT.md records a final browser-proof/quickstart.png receipt and notes that the committed openwiki/*.md pages were unchanged while openwiki/.entity-openwiki.json was refreshed. The generated wiki’s HTML presentation path is also guarded by CodeMirrorFileViewer reloading the same iframe source once after a deep-linked page loads, which keeps fragment navigation responsive inside the scriptless preview without widening the sandbox or replacing React-owned DOM. The same recent server fix now keeps oversized file reads on one shared 16 MiB limit across local, HTTP markdown, Docsify, and indexing paths, so the Files page and the release/runtime docs describe a single read boundary rather than multiple inconsistent ceilings. The entity-wiki source now boots from ./openwiki-html, and the generated HTML tree is indexed after markup removal so the wiki stays searchable without exposing the generated HTML as document content. The newer deployment safety work adds scripts/entity-readiness-poll.sh, which waits for /api/tasks to report a numeric count that reaches the preflight database count before restart proceeds, and the native managed-storage broker hardening that rejects absolute paths, ./.. segments, symlinks, and oversized I/O while serializing replace operations under a root lock. See the linked feature and platform pages for the canonical details; this quickstart only summarizes the current boundaries and navigation.
